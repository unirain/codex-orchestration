## Intent Traceability

用户从一个终端交代多项工作，按工作内容追问，在确实需要决定时介入。此次改进聚焦三个动作：看懂消息归属，回答一条具体问题，返回原来的草稿。本版独立规定终端交互行为与定向答复契约。

## Parent Architecture and Inherited Decisions

继承父规格 FR-001、FR-002、FR-003、FR-007、BR-005、BR-006、IR-010、SEC-011。普通输入进入默认来源 Thread，Worker 可直接承接明确的订阅追问；超出 Mandate 的新工作仍需交回、Eval 和 accept。后台生命周期独立于终端。本文标识只在本改进内使用。

## Verified Current Behavior and Baseline

| 使用场景 | 当前证据 | 用户能观察到的问题 |
| --- | --- | --- |

| 后台产生回执 | chat 每 750 ms 读取事件，用 console.log 写入带完整 Ticket ID 的文本 | 输入区和异步输出共用终端行，没有独立的草稿渲染 |

## Desired Delta and Invariants

- `FR-001`: 交互式 chat 默认打开新 TUI。用户原话按原文展示，界面用中文呈现收件、接单、待答、排队和失败状态。聊天正文、/status、详情与错误提示均须将宿主记录渲染为可读内容；原始协议 JSON 和内部路由信封在这些视图中的展示次数须为零。成功发送只表示宿主已收到；只有接单 Decision 已提交后才能显示「已接单」。用户可查看完整标识和 trace。同名任务通过简短标识区分。
- `FR-002`: 回执到达、窗口调整或切换待答问题时，正在编辑的普通消息须保留原文、换行和光标位置。普通输入支持中文、多行、粘贴和键盘提交。
- `FR-003`: 待答区展示当前有效的 Worker 问题、所属任务以及可执行的操作。用户主动选中问题后输入区显示「回复〈任务名〉」。即使只有一条问题，普通输入也继续走普通路由。Esc 取消回复并返回原草稿。
- `FR-004`: 状态区显示绑定仓库、连接状态和待答数量。重连时明确标出离线期间的消息，先呈现尚待回答的事项；旧历史可回看。首次打开没有已读位置时显示当前状态，并把历史标为历史。
- `BR-001`: 当指定 Ticket 仅因所选 Attention 等待答复时，提交动作标为「回复并继续」。宿主接受答复后，解除该问题造成的等待，按原 Mandate 和正常槽位规则恢复调度。槽位已满时显示「答复已保存，等待执行」；实际启动 turn 后才可显示执行中。若用户已主动暂停，提交动作标为「仅保存答复」，工单保持暂停，直到用户明确恢复。

示例：Worker 询问「第二天催促一次，三天的等待时间要重新算吗？」。用户原本在输入邮件任务，主动选择该问题，回复「继续从第一条未获回复的消息计时」。提交后显示答复归属及实际恢复状态，并还原邮件草稿。若问题只含自由文本，直接展示原文和文本输入框；只有来源提供了明确的结构化选项，才可显示选项。原始 Worker 文本保留原语言。

## Architecture and Technology Impact

在交互式 TTY 中采用 `@earendil-works/pi-tui` 常规主屏模式，组合消息区、独立编辑器、待答选择和状态栏。会话、调度、工具与权限继续由现有宿主管理。独立执行 say、status、show、trace 等一次性命令时，若标准输出连接终端，使用文字或表格展示结果；若标准输出接入管道或重定向到文件，沿用既有机器可读格式。错误沿用原有退出状态与错误流。格式转换由客户端完成。pi-tui 作为新的交互层依赖，其安装方式、最低 Node 版本以及中文输入法表现须在发版验收时验证。

## Data, Integration, Security, and AI Impact

- `DR-001`: 已读位置按本机客户端视图和仓库绑定隔离，和宿主的事件序号对应。翻页补读、重连和重复轮询不得把同一回执重复显示为新消息。客户端草稿仅要求在本次进程内保留。
- `IR-001`: 宿主向交互客户端提供任务标题、生命周期、暂停原因、有效问题标识及其版本。定向答复携带发送标识、Ticket、问题标识或版本、答复原文及用户选定的动作。宿主须将它关联到原问题，成功后返回已记录、等待执行或仍暂停的真实状态。答复记录、该问题的已答状态和适用的待调度操作须一致提交。中途重启后，同一答复至多交付一次。普通 say 和脚本的既有 JSON 接口保持兼容。
- `SEC-001`: 定向答复须通过现有本机写入鉴权。宿主核对仓库、Ticket、问题是否仍有效，并重新检查当前暂停原因与 Mandate。两个终端同时回答时至多一个答复生效；同一发送标识与相同内容重试返回原回执；复用标识却更换目标、内容或动作时须拒绝。若用户在看到「回复并继续」后又从另一终端暂停，提交时问题仍有效则保存答复并显示「已保存，仍暂停」；若暂停发生在答复提交后，按父规格 FR-007 冻结待执行动作或中断活跃 turn。问题过期、被替换或 Ticket 已结束时，保留输入供用户处理，拒绝错误投递。
- `AI-001`: 定向答复只作为该问题的输入证据，保留用户原话和工作归属。选中问题、按 Enter、选择建议选项均不能扩大 Mandate 或授予仓库写权限。超范围工作按父规格 BR-006 处理。Main 的澄清与 Worker 的 Attention 标明来源；本版定向答复限于已有稳定标识的 Worker Attention，Main 澄清沿用来源 Thread。
- `IR-002`: 存量记录缺少可靠的问题标识或暂停来源时，可展示记录并使用现有查看、暂停和继续命令，宿主不得据文本相似度推断可自动恢复。

## Performance, Reliability, Scale, and Cost

- `NFR-001`: 在同一终端进程内，中文多行输入到一半连续到达 20 条回执，回执按序各显示一次，草稿逐字一致且光标位置相同。此数值是验收负载。
- `NFR-002`: 连接中断时反馈未确认发送状态并保留草稿。以同一发送标识核对或重试，成功的输入只产生一次业务效果。打开界面、翻历史、编辑和切换焦点所产生的模型调用数为零。

## Regression Boundary

默认 Thread 的 fanout、hand-back、Eval、普通聊天新建 Ticket 的条件和远端操作授权继承父规格。CLI 退出后宿主继续工作。后台事件抢焦点、泄漏临时访问凭据、过期答复唤醒另一 Ticket、手动暂停被问答隐式解除，均判验收失败。

## Measurement, Observability, and Comparison

- `OBS-001`: 发起人可通过现有诊断入口按发送标识查到原话、当前去向、定向问题及去重结果。普通交互默认显示业务标题，诊断视图保留原始 ID。用相同输入序列对比当前 CLI 与候选 TUI，记录伪终端输入输出、宿主状态及消息回执；中文输入法另做真实终端走读。

## Rollout and Rollback

先在独立测试绑定验证候选界面，沿用受信任的本机 HTTP 连接。遇到旧宿主时，交互界面展示可读的兼容提示，并仅开放宿主支持的操作；旧客户端仍可读取兼容数据。回复结果未知时先对账再重试。若出现跨 Ticket 投递或错误恢复，停用定向答复入口，保留已形成的记录供追溯。

## Acceptance Scenarios and Evals

- `AC-001` verifies `FR-001`, `OBS-001`: 输入两条独立目标，第一条仅已收件时不得显示已接单。接单后两张 Ticket 以标题区分，默认视图中原始 Trigger JSON 出现零次，trace 能定位各自的原记录。
- `AC-002` verifies `FR-002`, `NFR-001`: 编辑含中文与换行的草稿，在行中移动光标；注入回执、改变窗口宽度、进入答复再 Esc，核对草稿、光标和消息顺序。
- `AC-003` verifies `FR-003`, `BR-001`, `IR-001`, `AI-001`: follow up 与邮件各有问题，选中前者回答。只有该问题收到答复，邮件保留等待；有空槽时原 Worker 收到答复并接续一次；满槽时答复仅排队，释放槽位后再接续一次。两种情形均核对 Mandate 原值、邮件 Ticket 的输入数和 turn 数。再发普通消息，观察默认订阅路由。
- `AC-004` verifies `SEC-001`, `IR-002`: 分别模拟双终端同时答复、旧问题被替换、回复过程中用户主动暂停、旧记录缺少暂停原因和无效凭据。手动暂停且问题有效时，答复只保存一次，新增 turn 为零；问题已替换或鉴权失败时写入为零，答复草稿仍在。两终端竞争同一问题，后提交者看到已处理状态。
- `AC-005` verifies `FR-004`, `DR-001`, `NFR-002`: 断开期间产生超过一页的回执，重连后区分历史和新增；另一终端的已读位置独立。模拟宿主写成功但回执丢失，重试只得到同一次发送结果。
- `AC-006` verifies `FR-001`, `IR-001`, `NFR-002`: 在伪终端启动 chat，发送消息，打开 /status 和任务详情，并模拟一次错误；核对所有系统回执均为可读文本。独立执行 status 和 trace 时也按可读视图展示。将 say、status、trace 的标准输出分别接入管道或重定向到文件，沿用原脚本解析结果，核对字段、退出码及输出中无 TUI 控制序列。界面空闲、浏览和编辑时核对零新增模型 turn；退出终端后原后台测试仍能完成。

## Constraints, Dependencies, Assumptions, and Risks

前提是宿主能区分人工主动暂停和等待问题所导致的暂停，并能证明问题身份。当前 status 返回问题文本，两类暂停不能仅靠显示值区分。旧记录缺乏可靠依据时按 IR-002 降级。更宽的用途如增加通用问答、天气查询、多 Session 手工管理及变更模型提供方，留在本次范围之外。
